Lab 5: Linear PID Control + Linear Extrapolation

This lab focused on using Time of Flight feedback to drive the robot toward a wall and stop at a target distance of 1 foot. I tuned proportional, integral, and derivative gains, added deadband logic, logged debugging data over Bluetooth, and explored linear extrapolation so the control loop could run faster than the ToF sensor update rate.

1. Prelab: Bluetooth Debugging Setup

For this lab it was important to build a debugging system that let me start the controller from my computer, run it for a fixed amount of time, and then send the collected data back over Bluetooth. Instead of placing all of the PID and ToF code directly inside loop(), I placed the main control behavior inside a Bluetooth command case named GET_ALL. This made it easy to send one command from Python and start the full data collection run.

How the Debugging Flow Works
  1. Send a Bluetooth command from the computer.
  2. Start the GET_ALL case on the Artemis.
  3. Run the PID controller for a fixed number of loop iterations.
  4. Store timestamps, ToF data, and motor outputs into arrays.
  5. Send the saved data back over Bluetooth after the run ends.
Why I Did It This Way

This setup made testing much easier because I could run the robot, stop the behavior, and then plot the saved data in Python. It also helped me identify controller bugs without constantly reprogramming the board.

Bluetooth Start Command Structure
switch (cmd_type)
{
  case GET_ALL:
  {
    // Start ToF + PID collection here
    break;
  }

  case END_PID:
  {
    // Force run to stop early if needed
    break;
  }
}

Inside GET_ALL, I used a main for loop to limit the total number of iterations. In my testing, I used a maximum loop count of 1000, which gave about 6-7 seconds of runtime. During this time I saved debugging data into arrays so I could inspect how the controller behaved.

Fixed-Length Data Collection Idea
for (int i = 0; i < 1000; i++) {
  // Read ToF data
  // Compute PID output
  // Save time, distance, and motor input into arrays
}

I also made a command called END_PID that can force the run to stop early. After the main loop exits, another loop begins and sends back the collected data over Bluetooth. This was useful for debugging because even incomplete runs still gave me enough information to inspect what went wrong.

2. Position Control Objective

The goal of this task was to have the robot drive toward a wall and stop at a distance of 1 foot (12 inches) using the Time of Flight sensor for feedback. Since the robot can move quickly and the ToF sensor does not update infinitely fast, the controller needed to be tuned so that it was fast enough to approach the target but not so aggressive that it would crash into the wall.

Target Setpoint

Desired distance from the wall: 12 in

3. Finding the Proportional Gain (Kp)

I first started tuning the controller using proportional control only. I tested several values of Kp to see how strongly the robot reacted to distance error.

Proportional Gain Values Tested
  • Kp = 0.1
  • Kp = 3
  • Kp = 3.5
  • Kp = 4
Chosen Value

I chose Kp = 3.5 because it gave a good balance between speed and stability for my robot.

With very small proportional gain like Kp = 0.1, the response was too weak to be useful. At Kp = 3, the robot moved toward the wall, but it still seemed slower than I wanted. At Kp = 3.5, the robot behaved much better and the response looked more reasonable. When I tested Kp = 4, the robot became too aggressive and ended up touching the wall.

Reasonable Kp Range

Based on my tests, a reasonable proportional gain range for my robot was about 3 to 4. Gains below that were too weak, while gains above that made the robot too aggressive near the wall.

Proportional Control Idea
error = setpoint - distance;
output = Kp * error;

4. Deadband Compensation

After getting proportional control working, I added a deadband feature to stop the robot from oscillating back and forth near the setpoint. Since the motors have static friction, very small motor commands do not always create reliable motion. This can make the robot jitter when it is already close to the target.

Deadband Rule

If the robot was within 0.25 inches of the target distance, I stopped both motors. This made the stopping behavior cleaner and reduced oscillation near the setpoint.

Deadband Logic
if (abs(error) <= 0.25) {
  left_motor = 0;
  right_motor = 0;
}

5. Finding Integral and Derivative Gains

After choosing a good proportional gain, I moved on to tuning the integral and derivative terms. These were harder to tune because even small changes caused noticeable differences in controller behavior.

Integral Gain Values Tested
  • Ki = 0.02
  • Ki = 0.01
  • Ki = 0.005
  • Ki = 0.002
Derivative Gain Tested
  • Kd = 0.3 in one test setup
  • Later tested together with Kp = 3.5

I had difficulty identifying a good starting point for the integral gain because there were massive differences in performance between values like Ki = 0.02 and smaller values such as Ki = 0.007. A lot of the values in between also felt awkward in practice. Because of that, I decided to test the integral and derivative gains together rather than tuning each one completely on its own.

Combined PID Starting Point

One of the first combined gain sets I tested was: Kp = 3.5, Ki = 0.02, and Kd = 0.8.

Why Add I?

The integral term helps push out steady-state error that may come from friction, motor mismatch, or small controller bias.

Why Add D?

The derivative term helps react to how quickly the robot is approaching the wall, which can help reduce overshoot and make the stop more controlled.

Tuning Difficulty

The biggest challenge was that small changes in Ki and Kd could create very different behavior, so testing had to be done carefully.

6. ToF Sampling Rate and Control Loop Timing

The Time of Flight sensor does not update as fast as the main control loop can run. This is important because the PID controller may be capable of running much faster than new sensor measurements are being generated. If the loop waits every time for a new ToF measurement, the controller speed becomes limited by the sensor.

Why This Matters

A faster control loop usually gives smoother and more responsive control. But if the ToF sensor is slower, then some iterations of the control loop have to work without a brand new measurement.

Lab Idea

The main goal here was to separate the ToF sensor rate from the PID loop rate so the robot could still react between measurements.

In this lab, the correct approach is to let the PID control run every loop, check whether a new ToF value is ready, and then either update the measurement or continue using the latest available estimate. This is what leads into linear extrapolation.

7. Linear Extrapolation

To improve control performance, I used the idea of extrapolating distance between ToF readings. Instead of reusing the same old data point whenever the sensor did not have a new reading ready, I estimated the robot’s current distance using the last two ToF measurements.

Linear Extrapolation Equation
slope = (d2 - d1) / (t2 - t1);
estimated_distance = d2 + slope * (t_now - t2);

The idea is simple: every time a new ToF value arrives, I save the most recent two measurements and calculate the slope. Then, until another new reading arrives, I use that slope to estimate the current distance. This lets the PID controller run faster than the ToF sensor itself.

8. Wind-Up Protection

Since I am completing the 5000-level version of the lab, I also need to include wind-up protection. Integrator wind-up happens when the integral term keeps accumulating error while the motors are already saturated or while the robot cannot respond properly. This can make the controller overshoot badly once the robot is finally able to move again.

Without Wind-Up Protection

The integral term can grow too large and keep pushing the robot too aggressively, even after the error starts shrinking.

With Wind-Up Protection

Limiting the integral term keeps the controller more stable and prevents extreme buildup from the accumulated error.

Example Integrator Clamp
integral += error * dt;

if (integral > integral_max) integral = integral_max;
if (integral < -integral_max) integral = -integral_max;

10. Conclusion

In this lab I created a Bluetooth-based debugging setup for running a linear PID controller with Time of Flight feedback. I first tuned proportional control and found that Kp = 3.5 worked well as a starting point for my system. I then added deadband logic to reduce oscillation near the 12 inch target and began testing integral and derivative gains to improve stopping behavior. Because the ToF sensor updates slower than the main control loop, I also explored linear extrapolation so the controller could continue updating between sensor readings. Finally, I considered wind-up protection for the integrator so the controller would remain more stable under real hardware limitations.
