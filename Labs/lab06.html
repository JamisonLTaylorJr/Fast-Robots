Lab 6: Orientation Control with IMU + PD

In this lab I used the IMU gyroscope to estimate the robot's orientation, then applied a PD controller to turn the robot to a desired heading. I built the controller so that Bluetooth commands could still be sent while it was running, tested multiple gain values, and evaluated performance using theta vs time plots, videos, and controller debugging data.

2. PID Input Signal

You should integrate your gyroscope to get an estimate for the orientation of the robot.

To estimate the robot's orientation, gyroscope data must be turned into a heading estimate. In this lab I used the onboard DMP from the ICM-20948 to get quaternion data, then converted that into yaw. This gave a cleaner estimate of orientation than doing a very basic raw gyro integration by itself.

Yaw Estimate from DMP Quaternion Data
icm_20948_DMP_data_t data;
myICM.readDMPdataFromFIFO(&data);

if ((myICM.status == ICM_20948_Stat_Ok) || 
    (myICM.status == ICM_20948_Stat_FIFOMoreDataAvail)) {

  if ((data.header & DMP_header_bitmap_Quat6) > 0) {

    double q1 = ((double)data.Quat6.Data.Q1) / 1073741824.0;
    double q2 = ((double)data.Quat6.Data.Q2) / 1073741824.0;
    double q3 = ((double)data.Quat6.Data.Q3) / 1073741824.0;
    double q0 = sqrt(1.0 - ((q1 * q1) + (q2 * q2) + (q3 * q3)));

    double qw = q0;
    double qx = q2;
    double qy = q1;
    double qz = -q3;

    double t3 = +2.0 * (qw * qz + qx * qy);
    double t4 = +1.0 - 2.0 * (qy * qy + qz * qz);
    Gyro_yaw = (float)atan2(t3, t4) * 180.0 / PI + 3.8;
  }
}

Are there any problems that digital integration might lead to over time? Are there ways to minimize these problems?

One major problem with digital integration is that small sensor errors accumulate over time. Even a small amount of noise or bias in the gyroscope can build up through repeated integration steps, which causes the estimated heading to drift away from the true heading.

To minimize this issue, the first step is sensor calibration. While the robot is stationary, gyro readings can be averaged and that bias can be subtracted during operation. Another improvement is using a precise timestep calculation. Low-pass filtering can also help reduce noise before it affects the estimate.

Does your sensor have any bias, and are there ways to fix this? How fast does your error grow as a result of bias? Consider using the onboard digital motion processor (DMP) built into your IMU to minimize yaw drift.

Yes, the gyroscope does have bias. Bias appears as a constant offset in the angular velocity reading, which means the heading estimate can drift even when the robot is not rotating. The larger the bias, the faster that error grows over time.

One way to reduce this drift is to combine gyroscope data with accelerometer data. The gyroscope is useful for smooth short-term motion tracking, while the accelerometer gives a longer-term reference. A complementary filter can combine these signals to improve stability. In this lab, the DMP was also useful because it performed sensor fusion internally and reduced yaw drift compared to a very simple raw integration approach.

Are there limitations on the sensor itself to be aware of? What is the maximum rotational velocity that the gyroscope can read? Is this sufficient for our applications, and are there ways to configure this parameter?

Gyroscopes have several limitations, including bias drift, measurement noise, temperature sensitivity, integration error, lack of an absolute orientation reference, and sensitivity to vibration. Since the gyroscope measures angular velocity rather than angle directly, any integration errors continue to grow with time.

The gyroscope range can be configured to different full-scale values depending on the IMU settings. For this robot application, the available range is more than sufficient because the robot does not rotate anywhere near the maximum measurable angular velocity. This range can be adjusted to balance sensitivity and measurement range depending on the task.

3. P / I / D Discussion

Kp / Ki / Kd values chosen and why

For this lab, I tested proportional and derivative control and chose to use a PD controller. I did not end up using an integral term because PD already did a good enough job for this orientation control task. The robot was able to turn toward the target heading with a reasonable response, and the derivative term helped reduce overshoot and oscillation.

A purely proportional controller can turn the robot toward the target, but if the gain is too high it may overshoot or oscillate around the setpoint. Adding the derivative term improves damping by reacting to how quickly the error is changing. Since the robot did not appear to need strong steady-state error correction for this lab, I kept the controller as PD instead of full PID.

Kp

Main turning response. Increasing Kp made the robot react more strongly to heading error.

Kd

Added damping. Increasing Kd reduced overshoot and helped the turn settle more cleanly.

Ki

Not used in the final controller because PD performance was already acceptable for this lab.

PID_dt_ori = (now - PID_time2_ori) / 1000.0;

4. Derivative Term Discussion

Does it make sense to take the derivative of a signal that is the integral of another signal?

In theory, taking the derivative of an integrated signal can recover rate information, but in practice it can amplify noise. Since the heading estimate already contains sensor noise and small drift, the derivative term can become noisy if it is not handled carefully.

Think about derivative kick. Does changing your setpoint while the robot is running cause problems with your implementation of the PD controller?

Yes, a sudden setpoint change can cause derivative kick because the derivative term reacts strongly to rapid changes in error. This can create a spike in motor command. One way to reduce this is to base the derivative term on the measured output instead of only the error.

Is a low-pass filter needed before your derivative term?

A low-pass filter is helpful because the derivative term is sensitive to noise. Filtering the signal before taking the derivative makes the controller more stable and prevents the motors from reacting to tiny noisy fluctuations.

Range / Sampling time discussion

8. (5000) Wind-Up Implementation and Discussion

Implement wind-up protection for your integrator. Argue for why this is necessary.

Even though I did not use integral control in the final version, wind-up protection is still important to understand. Integrator wind-up happens when the control output saturates but the integral term keeps accumulating error anyway. Once the robot finally starts responding, that built-up integral can cause large overshoot and slower settling.

Wind-up protection is useful because it makes controller behavior more consistent across changing conditions such as floor friction, battery level, or motor differences. Common fixes include clamping the integral term or only allowing it to accumulate when the actuator is not saturated.

Example Anti-Windup Logic
error1I_ori += error1P_ori * PID_dt_ori;
